## Context

Three things established across prior revisions of this change are load-bearing for this revision's approach.

**1. The first two confirmed root causes are narrower than "nullable-type unions are unsafe."** Reading OpenCode's Gemini schema converter (`packages/llm/src/protocols/utils/gemini-tool-schema.ts` in `anomalyco/opencode`, `main` branch) showed the plain `type: ["T", "null"]` array shorthand converts cleanly to Gemini's native `{type: T, nullable: true}` for scalar/object fields — no `anyOf`, no corruption. The two breakages reported before this change started are narrower:
   - `enum` arrays containing a literal `null` — `schemars`' rendering of `Option<Enum>` — get corrupted by the converter's `value.map(String)`, since `String(null) === "null"` in JavaScript, injecting a bogus enum value that matches no real variant. Confirmed by reading the source and reproducing it directly.
   - `format: "uint64"` — not a value Gemini's legacy `Schema.format` recognizes for `INTEGER` fields (only `int32`/`int64` are documented).

**2. The host requires `strict: true` fleet-wide, with no per-tool exception.** An earlier revision's conclusion — stop chasing literal `strict: true`, document `update_note_properties` as the one open exception — isn't viable under this constraint. Every tool must genuinely qualify, which means structurally-awkward cases (an optional enum, a caller-defined-key object, a nullable array) need redesign rather than documentation.

**3. Live verification (this revision) confirmed most of the design and found two more real, narrow problems.** With OpenCode already holding valid OpenAI/Anthropic/Google credentials in this environment, four things were tested directly instead of reasoned about from source:
   - **OpenAI `strict:true`**, hit directly with the real `recall_memory_notes` schema (nullable arrays, `minimum`, everything): accepted cleanly, produced a correct tool call. No changes needed on the OpenAI side.
   - **Anthropic `strict:true`**, same schema: rejected with `"For 'integer' type, property 'minimum' is not supported"`. A follow-up minimal request isolated that `minLength` (present on every scope field, fleet-wide) is fine — only `minimum`/`maximum` on integers is the problem. This is a real, previously-unknown gap: every tool with a `limit`/`offset` field was not actually Anthropic-strict-eligible despite passing the earlier source-only review.
   - **Gemini's raw API**, hit directly via `parameters_json_schema` with a minimal nullable-array field: accepted cleanly, correct tool call with `null` for the array. Confirms the array-null shorthand is fine at the API level.
   - **The actual installed OpenCode client** (the running binary, not a fresh `main`-branch checkout), driving a real session against a local build of the already-fixed Muninn with a Gemini model: a genuine 400 from Google's API, `properties[updates].any_of[0].items: missing field`, for exactly the two `Option<Vec<T>>` fields in the whole fleet (`evolve_core_persona.updates`, `recall_memory_notes.filters`). Since Gemini's own API and OpenAI/Anthropic strict mode all accept the identical nullable-array shape without complaint (the three points above, all tested against the *same* schema fragments), this is conclusively a bug in the installed OpenCode client's own legacy-`Schema` conversion — not a Gemini or strict-mode limitation. It's still worth working around, since it's exactly the client this deployment runs behind and the fix is cheap.

   Investigating the fourth point surfaced a better design for `evolve_core_persona` than the one already shipped (see Decisions): the earlier fix addressed the enum/`null` bug by dropping the single form's `which` from a schema `enum` to a plain nullable string, but the real source of awkwardness was having two argument forms in the first place. Collapsing to the batch form only removes the nullable-array problem as a side effect, for free.

## Goals / Non-Goals

**Goals:**
- Every tool's input schema is genuinely eligible for OpenAI's and Anthropic's `strict: true`: every property, root and nested, in `required`; `additionalProperties: false` everywhere; nothing that violates either provider's supported-keyword list — including, as of this revision, no `minimum`/`maximum` on numeric fields.
- No schema anywhere emits a literal `null` inside an `enum` array, the unrecognized `format: "uint64"` value, or a nullable array field that the deployed OpenCode client mishandles — all eliminated fleet-wide.
- `evolve_core_persona`, `update_note_properties`, and (as of this revision) `recall_memory_notes.filters` are redesigned so their genuinely-dynamic aspects are expressed in a form a closed schema can describe, without losing capability.

**Non-Goals:**
- A schema *variant* per provider. Muninn emits one schema.
- Changing `update_note_properties`'s merge semantics, link-expansion behavior, or response shape — only its *input* shape changes.
- General-purpose defense against every possible bug in every possible MCP host's schema-conversion layer. The `updates`/`filters` fix in this revision is adopted because it's cheap (an empty array was already handled identically to absent/`null` by both handlers) and because it happens to coincide with an independently-motivated design simplification for `evolve_core_persona` — not because Muninn is taking on open-ended responsibility for third-party client bugs.

## Decisions

**Consolidate `evolve_core_persona` to a single always-`updates` form; `which` reverts to a real enum.** The prior revision's fix for the `which`/`null`/`enum` bug — retype the single form's `which` to `Option<String>`, dropping its schema `enum` — is superseded, not built on. The two-form design (`which`+`content` *or* `updates`) was already the reason `which` needed to be nullable at all: only the top-level single form's `which` could be "not this one, using the other form instead." Remove the top-level single form entirely — every call, including what used to be a one-file update, goes through `updates` (required, 1–5 entries, no duplicate `which`) — and there is no longer any context in which `which` needs to represent "no value": `EvolveUpdateEntry.which` was always required already, so it goes back to being a clean, always-required, null-free 5-value `enum` (strictly better than the string-only fallback — schema-level guidance restored). This also means `updates` is no longer a *nullable* array (`type:["array","null"]`) — it's a plain required array, which is exactly the shape the live OpenCode/Gemini test showed is safe, and the nullable-array shape that test showed is broken never appears for this tool again. One redesign fixes two independent problems.

  Response shape unifies to always `{ results: [...] }` (previously the single form returned bare `{ bytes_written }`); with only one calling form, having two response shapes had no remaining justification.

  **Considered and rejected, again, now with the added information:** keeping two forms and inventing a 6th sentinel enum value (`"batch"`) for `which` — still rejected, and now for an additional reason beyond the one recorded in the prior revision: it wouldn't have fixed the live-verified `updates`-array bug, since the array would still need to be nullable to signal "single form in use instead." Splitting into two tools — still rejected as more invasive (a new public tool name) than a single-form consolidation that achieves the same properties.

**`recall_memory_notes.filters`: drop `Option`, use an empty array as "no filters."** Unlike `evolve_core_persona`, there's no alternative-form restructuring available here — `filters` is one of several independently-optional predicates (`query`, `regex`, `filters`, `modified_after`, `modified_before`), not an alternative to something else. The fix is the direct analog of the array half of the `evolve_core_persona` decision: make `filters` a required, non-nullable `Vec<PropertyFilterField>`; an empty array means the caller supplied no property filters. `parse_filters` already treats `None`, `Some(Value::Null)`, and `Some(Value::Array(empty))` identically (an empty `for` loop produces the same `Vec::new()` either way), so this needs no handler-logic change — only the schema-facing Rust type changes from `Option<Vec<T>>` to `Vec<T>`. The requirement that "at least one of `query`/`filters`/`regex`/`modified_after`/`modified_before` be supplied" is unaffected in spirit: an empty `filters` array still doesn't count as "supplying filters," exactly as an absent one didn't before.

**Strip `minimum`/`maximum`/`multipleOf` fleet-wide, alongside the existing `format:"uint64"` strip.** Live-confirmed: Anthropic's `strict:true` rejects `minimum` on integer fields outright, and every `limit`/`offset` field in the fleet carries one (`schemars`' rendering of a `u64` type, or an explicit `#[schemars(range(min = 1))]`). `multipleOf` isn't currently emitted anywhere in the fleet, but is stripped defensively since it's the same class of numeric-range keyword and Anthropic's documented "not supported" list names it alongside `minimum`/`maximum`. This is folded into the same normalize pass that already strips `format:"uint64"` — one recursive walk, more keys stripped.

**Reunify the `additionalProperties: false` pass and the full-`required` pass into one normalize step.** (Carried over from the prior revision, unaffected by this one.) One recursive walk — for every closed-shape object node with a `properties` key: set `additionalProperties: false`, set `required` to the full `properties` key list — covers both concerns.

**`update_note_properties`: replace the object argument with a JSON-encoded string (`properties_json`).** (Carried over from the prior revision, unaffected by this one — see that revision's reasoning: the blocker is dynamic *value types*, not dynamic keys, and there's no closed way to declare "any JSON value," so the whole object is pushed one level down into an opaque string the schema doesn't try to describe.)

## Risks / Trade-offs

- **[Risk]** All three redesigns this revision touches (`evolve_core_persona`'s consolidation, `filters`, and the carried-over `properties_json`) are genuine breaking changes to calling convention, not just schema-shape changes. Existing `evolve_core_persona` single-form callers must switch to `updates`; existing `recall_memory_notes` callers that omit `filters` must now send `[]` explicitly under strict-mode tool calling (though, as with the rest of the fleet, a caller that simply omits an optional-in-spirit key still works — the handler doesn't enforce presence, only the advertised schema's `required` list changed); existing `update_note_properties` callers must switch to `properties_json`. → **Accepted**: the host's fleet-wide `strict: true` requirement makes this unavoidable, and in `evolve_core_persona`'s case the same redesign also fixes a live-verified bug.
- **[Risk]** This revision's confidence is now grounded in live tests (OpenAI strict, Anthropic strict, Gemini raw API, and the actual installed OpenCode client) rather than source reading alone for the specific claims tested — but the live tests covered representative schemas and a handful of targeted minimal cases, not literally every field of every tool. → **Mitigation**: the task list's final verification step should re-run the same live checks against the regenerated schemas before considering this revision proven, the same discipline that surfaced the `minimum` and OpenCode-array findings in the first place.
- **[Trade-off]** `evolve_core_persona`'s common one-file case goes from two flat top-level strings (`which`, `content`) to a one-element array of an object (`updates:[{which,content}]`) — marginally more nested for the simplest call, in exchange for a single calling convention, restored schema-level `enum` guidance, and no nullable array anywhere in the tool.
- **[Trade-off]** `properties_json` loses JSON-Schema-level structural guidance for its content (a strict-mode client sees only "a string," not "an object of frontmatter keys"). Accepted for the same reason as the prior revision: it's the only way to keep full value-type flexibility while staying schema-closed.
